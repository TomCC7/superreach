# Adapt to a New Arm

Start with a fixed-base arm with six hinge joints. The OpenYAM pipeline is a reference implementation, not a drop-in robot configuration. Make the port in a separate checkout and keep the published artifacts intact. This guide covers simulation only.

## 1. Prepare the MJCF and check the servos

- Use [`prepare_model.py`](../data_gen/prepare_model.py) as the adapter template. It reads OpenYAM's MJCF, URDF and meshes from `openyam-description/openyam_single/` under `SUPERREACH_GEN_DIR`. Point the adapter at your assets and update the joint names, TCP body/site, gripper constraints and collision exclusions. Keep the same actuated joint order in the planner, compiled model, data and policy. The reference uses `arm_tcp` and `arm_tcp_site`; the reduced planner fixes the fingers without removing their bodies or inertias. Compare TCP poses and collision decisions in RoboPlan and native MuJoCo before sampling trajectories.
- Use the new arm's joint ranges and planning velocity/acceleration limits when producing `limits.yaml`. In the simulation MJCF, check actuator transmission, position-servo `kp`/`kv` and `forcerange`, and any joint-level `actuatorfrcrange`. Test unloaded and loaded holds and small steps in native MuJoCo; check settling, contacts and delivered torque in both directions. OpenYAM's reference gains are `Kp = [50, 60, 50, 25, 15, 10]` and `Kd = [3, 4, 3, 2, 1, 0.8]`. These are simulation values, not gains for the new arm. The GPU plant applies its own `PEAK` force limits, so inspect the loaded plant as well as the XML.
- Keep the planning models separate from the training scene. The preparation script writes `runtime.xml` and `planner.xml` with a 1/60 s timestep. The registered training plant and browser use ten 2 ms physics steps per 50 Hz policy tick. Check the effective timestep and servo settings in each runtime.

## 2. Regenerate the training data

1. After adapting the generator, follow the [data generation setup](../data_gen/README.md) in a fresh `SUPERREACH_GEN_DIR`. From the repo root, run `python data_gen/prepare_model.py`, then `python data_gen/generate_bank.py` to seed the bank. The seed generator samples collision-free endpoints, runs RoboPlan RRT, shortcuts the path, and time-parameterizes it with TOPPRA. It stores `time_s`, `q`, `dq`, `ddq`, and TCP position and WXYZ quaternion in the shards. Inspect the seed previews and check that TCP labels match forward kinematics for the new scene.
2. Expand with `python data_gen/bulk16k.py`, or use `python data_gen/bulk16k.py --init-only` followed by `python data_gen/pool_generator.py`. Use one writer. Keep the `bank-full-v2` directory name expected by the [50 Hz loader](../gpu_train/runtime/openyam-50hz-supermimic-6d-v1/alignment.py). Preserve train/dev IDs, shard digests and manifest-relative paths, including the sibling `bank/` directory. Check resampling on both splits.
3. Build canonical inertial rows on the new **training** scene. [`generate_payload_catalog.py`](../data_gen/generate_payload_catalog.py) copies five canonical rows and adds variants using the `hand` body and a hard-coded attachment offset and load distribution. Adapt those assumptions and register the new canonical archive digest before running `python data_gen/generate_payload_catalog.py --scene "$SCENE" --canonical "$CANONICAL" --output ./data/generated/continuous_variants.npz`. Set `SCENE` and `CANONICAL` to your training XML and canonical NPZ. Do not reuse OpenYAM rows: the catalog includes compiled MuJoCo constants, not just masses. Check the new catalog against native MuJoCo at zero and nonzero payloads.

## 3. Adapt and check the GPU recipe

- [`run_train.py`](../gpu_train/run_train.py) selects the tri-mode recipe and only admits the registered OpenYAM scene, bank manifest and catalog. In your port, register new hashes (`SCENE_SHA`, `BANK_SHA`, `PAYLOAD_SHA`) and keep the admission checks. Use the `robot`, `trajectories` and `catalog` subdirectories of the directory passed to `--data-dir`.
- In the GPU [plant](../gpu_train/runtime/openyam-peaktorque-softpenalty-fresh-v1/openyam.py), check the `(nq, nv, nu) = (8, 8, 6)` assertion, the `:6` arm slices, finger reset, TCP and payload body, and force overrides. In the [EEF experiment](../gpu_train/runtime/openyam-50hz-policyik-eef-v1/experiment.py) and [tri-mode actor](../gpu_train/runtime/openyam-50hz-policyik-eef-v1/tri-mode-dual-enc-dr10ms-joint075-15k-v2/actor.py), update `q_nom` and `HOME` together; OpenYAM uses `[0, 1.047, 1.047, 0, 0, 0]` radians. The [tri-mode trainer](../gpu_train/runtime/openyam-50hz-policyik-eef-v1/tri-mode-dual-enc-dr10ms-joint075-15k-v2/train.py) reads arm limits from the first six MJCF joint ranges. If the arm layout changes, trace those dimensions through FK, the bank loader, history, goals, actions and evaluation rather than changing only the model assertion.
- Follow [GPU setup](gpu-training.md). After registering the port, use `--check-data` on `python gpu_train/run_train.py --data-dir ./data --out-dir ./runs/new-arm` to check admission. With `CUDA_VISIBLE_DEVICES=` and a fresh output directory, use `--verify-cpu` to exercise the native diagnostic after adapting its robot-specific checks. Then try a short GPU run with `--updates` before committing to full training.

## 4. Export and test in the browser

1. Align the deployment [`plant.py`](../superreach/plant.py), [FK](../superreach/geometry.py) and [actor](../superreach/actor.py) with the training model. The exporter loads matching actor weights and checks the FK buffers; it does not convert an arbitrary architecture. Extract the actor state dict from your training snapshot and use a matching deployment actor. From the repo root, run `python -m superreach.export --scene "$SCENE" --checkpoint "$CHECKPOINT" --output "$ONNX"`, with `SCENE` pointing to the matching export scene (meshes beside it in `meshes/`), `CHECKPOINT` to the actor weights, and `ONNX` to a new output file. Export checks PyTorch/ONNX parity.
2. Keep the tri-mode ABI if possible: `[1,318]` holds 16 frames of `(q6, dq6, previous q_des6, valid)`, 7 pose values (XYZ and WXYZ), 6 joint targets, and 1 mode code. The output is `[1,6]` absolute joint angles in radians. A different joint count requires changes to the exporter, JS compiler and runtime, not just a manifest edit.
3. Stage a separate copy of the [static bundle](artifacts.md). Update the scene and mesh hashes in `assets/BUNDLE.json` and add your ONNX path and SHA-256 as a `tri-mode-v2` checkpoint. Set `default_checkpoint` and update the selector in [`index.html`](../web/index.html). Run `python tools/export_onnx_to_jsbin.py "$SITE"` on that staged directory with the ONNX files referenced by the manifest. It generates the descriptors, JS graphs and float32 weights. The stock [`build_web.py`](../tools/build_web.py) expects the pinned demo bundle; it will not accept a new arm's files unchanged.
4. Match `HOME`, `KP`, and `KD` in [`policy.js`](../web/js/policy.js); update TCP lookup, gripper reset, payload attachment and joint handling in [`sim_worker.js`](../web/js/sim_worker.js). Serve with `python -m http.server 8000 --bind 127.0.0.1 --directory "$SITE"`. Adapt [`browser_smoke.py`](../tests/browser_smoke.py) to your checkpoint and compare JS joint commands against CPU ONNX on the same observations. Exercise each goal mode and a payload change in the browser. Inference runs in JavaScript; physics runs in MuJoCo WASM.
